# SmartMerge 产品边界与能力契约（讨论稿）

- 状态：产品约束 / 设计依据，非最终 PRD，非已实现功能清单
- 日期：2026-11-19
- 来源：真实 Excel 名录回收核对场景。遵循 requirements-clarity（Why / Simpler）及 product-designer（persona/JTBD、可测试 FR、人本设计）的分析方法。
- 当前目标：保持 ExcelMerge 可靠的两文件比较基础，逐步扩展为**无 AI 也可完成的 Excel 多版本修订、名录范围核查和安全合并**。LLM 为可选的业务语义助手。

## 用户工作方式与非目标

用户将完整总表直接分发给多人；参与者在 Excel 中独立修改，返回完整表或部分回传；汇总人需要查出谁改了什么、原来是什么、是否丢失原有名录、是否更名、是否修改了分工范围外的数据，并将确认后的修改合并回总表。

不开发文件分发平台、群发、账号权限平台、在线实时协作；不强制参与者安装 SmartMerge 或逐单元格点击批准。审核员以**Word 式修订审阅**方式查看高亮、前后值、提交来源，决定异常项；一个文件级合并确认不冒充逐单元格审核证据。

## 责任边界（必须保持）

| 职责 | SmartMerge 的确定性程序 | LLM（可选） | 不得擅自推断 |
|---|---|---|---|
| Excel 文件/格式 | 读取和保留值、公式、样式、红色标题和红色单元格的原始格式信息；定位 Sheet/行/列，保留可追溯坐标 | 将“标红列重点核查”解释为针对原表样式的查询计划 | LLM 不能凭文字猜测哪些单元格是红色 |
| 匹配与差异 | 验证唯一键/联合键、跨版本对齐、单元格比较、识别新增、缺失、改名和冲突 | 解释差异，提出低置信度匹配候选，须人工确认 | 改名不自动认定删除+新增；无稳定标识时不可伪装确定 |
| 范围规则 | 通过列标题执行包含/不包含、等于、不等于、空值、AND/OR、组合括号；绑定**原始总表快照**、处理结果可复现 | 将自然语言变成可编辑的通用规则计划 | 不把“河南/黄河流域/南水北调”写死在代码里 |
| 回收核查 | 按每人的原始核对范围核对覆盖情况；标记缺失、疑似删除、越界变更、改名及主键异常 | 识别需要特别注意的异常并解释原因 | 未修改 ≠ 未核对；无法断言由谁实际编辑了单元格 |
| 审核 | 标记、筛选、定位、前后对照、来源、选择、撤销、审计轨迹 | 判断说明是否具体、提示语义风险并列出证据 | 不凭空声称资料真实/人实际核对过 |
| 合并/入库前处理 | 确定性的变更归并、冲突禁止自动覆盖、预览、回退、格式保留、导出和可重复执行的转换 | 生成候选规则和转换计划，解释不确定性 | LLM 不直接写入正式数据、不绕过用户确认 |

## 产品交互基本面

1. **基准表** + 1..N **回传版本**：让用户直观看到“原始总表”和“来源文件/提交人”，而非 N² 个文件间互相比较。
2. **修订审阅**：表格中高亮变化；单击差异打开紧凑详情（原值 → 修改值、源文件、记录主键/位置、其他人同位置修改）。不把删除线和长批注塞满表格。
3. **查看模式**：全部 / 仅差异；再按新增/修改/删除、提交人、工作表、核对范围、异常类型筛选。筛选结果不能改变导出结果或误将隐藏行视为删除。
4. **规则构建器**：选列、选比较方式、填写值，AND/OR 分组，多条件组合；先在原始总表预览命中多少行，再保存为可复用的“核对范围”。自然语言只是生成这些规则的另一种输入方式。
5. **核对报告**：应核对记录数 / 回传找到数 / 记录缺失 / 名称变更 / 越界修改 / 未匹配 / 冲突。完整回传中的缺失可标为“疑似删除”；部分回传中的缺失只能标“未提供/待核实”，不能凭缺失认定删除。
6. **汇总导出**：无冲突变更展示为建议合并预览；冲突须选择方案；一键确认导出新文件，原件不覆盖。保留字段级来源及人工选择记录。

## 数据不变量

- **原始快照不可变**：范围规则绑定基准版本，不在回传版重新筛选而漏掉被改名、改区域的记录。
- **原始身份优先**：先使用唯一的稳定 ID，其次经验证的联合键；重复、空键、匹配歧义必须中止该记录的自动合并。
- **来源不可丢失**：提交人/来源文件是“提交来源”，没有文件级编辑审计时不声称是实际编辑人。
- **记录与修改是分开的对象**：基准记录、回传版本、单元格变更、人工审核决定、生成成果彼此区分。
- **规则是数据，不是硬编码**：可编辑、保存、重放；同一规则输入相同快照应得相同结果。
- **导入顺序不影响无冲突合并**：同字段同值归并一次，不同字段独立合并；同字段异值、删除与修改必须进入冲突队列。
- **人工主权**：所有正式写出前有影响范围预览、撤销和非破坏性导出。

## 当前源码核查与真实差距（2026-11-19）

- 当前 GUI `DiffView` 主要接收两份文件（src/dst），尚非正式 N 份回传合并工作流。
- `ExcelReader.Read` 使用 `ExcelUtility.GetCellStringValue` 并创建只含值和原始坐标的 `ExcelCell`；尚未将 NPOI 字体色、填充色、条件格式和公式元数据保留到核心模型。**因此“核对标红列/标红单元格”目前不可声称已实现**。
- `ExcelSheet.Diff`、`RowKeySelectionEngine` 和 `DiffGridModel` 已有两文件智能差异、单/联合主键、差异行分类筛选基础；需要避免由不安全主键自动匹配导致误删误合。
- 现有可编辑目标表功能是两文件场景的能力，不等于多回传合并审核；不能用“复制黏贴的人工拼表”冒充自动可靠合并。

## 实施顺序（每段必须可独立验收）

**M0 — 保护现有产品质量**：保留两文件比较、行/列分类、主键分析、TSV/CSV 和编辑功能；增加回归覆盖（尤其删除行过滤、改名、行重排、复制换行），不要退化旧版。

**M1 — 原始数据与范围规则基础（无 LLM）**：保留样式/公式必要元数据，明确识别红色字体/填充与条件格式的支持范围；做可视化规则构建器，支持多列 AND/OR/包含/排除，原表绑定和匹配预览；按原表范围核查两文件回传。

**M2 — 修订审阅与核查（无 LLM）**：可见的 Word 式变更卡片/来源/前后值，针对每份完整或部分回传做名录完整性、改名、疑似删除、越界修改检查；异常可定位到原始 Sheet 和单元格。

**M3 — N 版本合并（无 LLM）**：基准表+N 回传、变化来源、相同字段冲突、按人筛选、预览/撤销/导出、决策记录和审计报告。先交付正确的最小闭环，不扩张成协作办公平台。

**M4 — LLM 业务理解（可关闭）**：从通知文本生成“范围+检查项目+解释+待确认假设”；审阅确认后调确定性引擎执行；语义类检查返回依据与不确定性。关闭 LLM 时 M0–M3 必须继续正常运行。

**M5 — 入库前处理（按真实任务推进）**：字段映射、标准化、转换预览、校验报告、可审计导出。不可无预览直接覆盖源数据或写入正式数据库。

## 核心端到端验收例

- 总表 A=河南、B=黄河流域、C=工程名称不含南水北调，规则命中的集合应固定在原始版本。参与者改掉 C 以致规则不再命中，仍必须出现在审核范围并标记更名。
- 张工负责范围内原有 120 条；完整回传只找到 117 条，报告 3 条疑似删除；若标为部分回传，则为 3 条未提供/待确认，不认定删除。
- 某工程被两人改成相同值只应用一次；改成不同值要显示冲突；改变导入顺序不得改变最终无冲突结果。
- 原始红色列名和红色单元格被回传文件清除颜色后，仍应依据**原始模板**提醒核对；颜色来源识别不支持的样式应明确提示。
- 参与者将“不掌握”改为“因监测站2025年停运无法提供”，程序判断非空，LLM 可提示说明更具体，但不得自行断言停运属实。
- 测试在**未启用 LLM** 的情况下执行基础对比、筛选、来源追溯和导出，结果正确且可以用真实 Windows 窗口操作。

## 关键未解决问题（故保持讨论稿而非 PRD）

- 真实表格是否有长期稳定的工程编号，哪些情况下必须用联合主键？
- Word 式修订的“接受/保留原值”是否应该作为可选批处理操作，哪些场景必须逐条人工确认？
- 大文件、复杂公式、合并单元格、条件格式、宏工作簿的保真边界及目标性能，需要真实样本测试后确定。

## 评价标准

北极星：使用者能否在不破坏原表的情况下，**在真实核对任务中找到应核对的异常、看清每个修改来源、可靠生成一份新的总表**。不以代码行数、AI 调用次数、规则数量、UI 面板数量作为目标。
